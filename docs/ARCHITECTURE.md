# Architecture

furnest watches furnished-rental listing sources, matches what it finds against one set of search criteria, posts matches to a Discord channel, sends inquiry emails, and tracks each property through a review pipeline in a web dashboard.

This document is the reference design. Each part is built by a tracked issue, and this file changes along with the code.

## Guiding decisions

- **One versioned criteria profile, one Discord channel.** The app serves a single searcher. Criteria are versioned so that matches can always be explained against the version that produced them.
- **US-first, but not US-only.** Address parsing (usaddress) and currency (USD) sit behind interfaces, so other locales can be added later without touching the matching code.
- **No personal data in the repo.** Domains, emails, names and locations come from environment variables or DB-stored settings. Examples use `example.com` and placeholder values.
- **Prefer official APIs and feeds, fall back to scraping.** Scraping is polite (low volume, robots.txt where feasible) and degrades gracefully: a blocked source records a failure and never crashes the worker.

## Process model

One container image runs three commands, all sharing a SQLite database on the `/data` volume:

| Command | Role |
|---|---|
| `furnest web` | FastAPI app: dashboard (Jinja2 + HTMX, no JS build step), Bearer JSON API, `POST /discord/interactions`, `/healthz`, `/readyz`, optional `/metrics`. |
| `furnest worker` | Scheduler: one job per enabled source on its own interval with jitter. Also drains the DB job queue (inquiry sends, enrichment, criteria re-runs, Discord message sync) and writes a heartbeat. |
| `furnest migrate` | Applies Alembic migrations once and exits. Web can also auto-migrate on start. |

`furnest healthcheck web|worker` is each container's health probe: `web` asks its own `/healthz`, `worker` checks that the newest heartbeat is fresh. Both compose files run `migrate` as a one-shot service that must exit 0 before `web` and `worker` start (both refuse an out-of-date schema). The app runs as uid 10001, with the venv root-owned and read-only. The entrypoint starts as root only to take ownership of `/data`, since a bind mount that Docker creates is root-owned, then drops privileges. A build arg adds Playwright and Chromium for sources that need a browser.

SQLite runs in WAL mode with `busy_timeout` and foreign keys on, so web and worker can share it safely. The worker does all slow or network-bound work. The web process only reads, writes small rows, and enqueues jobs.

```
             ┌──────────────┐  enqueue jobs   ┌──────────────┐
 Browser ───▶│  furnest web │────────────────▶│ furnest      │──▶ listing sources
 Discord ───▶│  (FastAPI)   │◀── SQLite WAL ─▶│ worker       │──▶ SMTP / IMAP
             └──────────────┘    on /data     │ (scheduler)  │──▶ Discord REST, geocoder
                                              └──────────────┘
```

## Key mechanics

**Listing flow.** worker → adapter `search(criteria)` → `NormalizedListing`s → upsert (exact dedup on `(source, source_id)`, price history, `last_seen`) → group into a `Property` → match (hard filters pass/fail + 0–100 score with a breakdown) → `suggested` → Discord notification job. Listings no longer seen move their property to `unavailable`.

**Ingestion.** `ListingIngestor` (`pipeline/ingest.py`) runs one adapter once, and the scheduler (`pipeline/schedule.py`) calls it. Without an active criteria profile it does nothing. Otherwise it opens a `source_runs` row (`running`), calls `search` with the active criteria and passes the results to `SqlListingStore` (`db/listing_store.py`). Listings are deduplicated exactly on `(source, source_id)`, and a repeat within one batch keeps the last. A new listing is stored with its photos (`listing_images`) and first price. A listing seen before gets a new `last_seen`, and its data and photos are rewritten only when its content hash changes: a SHA-256 of the listing's JSON with amenities sorted, ignoring `first_seen`, `last_seen` and `raw`. `first_seen` never moves. `price_history` gets a row whenever the price (amount, range, currency, period) differs from the last recorded one, so it holds changes, not sightings. A listing that loses its price keeps the last known one. Every active listing of the source that the run didn't return gets `missed_runs + 1`, and is marked `removed_at` once it has missed `SOURCES_REMOVE_AFTER_MISSED_RUNS` runs *and* gone unseen for `SOURCES_REMOVE_AFTER_HOURS`, so neither one short search nor a long outage removes anything alone. Seeing it again clears both (relisted). The run row is then finished as `success` with found, new, updated (changed or relisted) and removed counts. If the search or the store raises, it is finished as `failed` with the error, nothing is marked missing, and the exception propagates to the scheduler. After the write commits, which keeps slow LLM calls off SQLite's single writer, each new, changed or relisted listing has its amenities extracted (stored on the row) and goes through `match_listing`. The result goes to a sink, which discards it until #28 connects properties. A listing whose extraction or matching fails is logged and skipped. The full `NormalizedListing` is kept as JSON in `listings.data`, so it reads back exactly. `listings.property_id` points at the listing's property (`properties`, set to NULL if the property is deleted).

**Photo hashes.** The `images.hash` worker job (`pipeline/images.py`, every `IMAGES_INTERVAL_MINUTES`) takes up to `IMAGES_BATCH_SIZE` photo URLs that have neither a hash nor an error, from the first `IMAGES_PER_LISTING` photos of active listings. Hash state is shared by URL (`db/image_store.py`): a URL another row already hashed is copied without a fetch, a result is written to every row with that URL, and `SqlListingStore` keeps the state of URLs a listing still has when it rewrites its photos. `ImageFetcher` (`dedup/phash.py`) downloads into memory only, obeys the image host's robots.txt when `SOURCES_RESPECT_ROBOTS` is set, rate-limits per host, requires an `image/*` content type and stops past `IMAGES_MAX_BYTES`. `compute_phash` refuses images over `IMAGES_MAX_PIXELS` before decoding them and returns imagehash's 64-bit pHash as 16 hex digits. A failure is stored in `hash_error` and not retried. `hamming`, `min_distance` and `matching_pairs` compare hashes for grouping (#50), where two photos at most `DEFAULT_MATCH_DISTANCE` (8) bits apart count as the same picture. The job runs outside source runs, so a slow image host can't time out a scrape. After a run, the listings that gained a hash are passed to `PropertyPipeline.regroup`, so grouping can compare their photos.

**Grouping.** Listings of the same unit on different sources share one `Property` (`GROUPING_*`, on by default). `SqlPropertyStore._ensure` stores each listing's address keys (`listings.address_key`: the canonical address; `street_key`: number, street and ZIP without the unit) and, for a listing without a property, calls `group_listing` (`db/grouping.py`) in the same transaction, before the match can notify anyone. Candidates are live properties with a listing at the same address key or street key, or inside a `GROUPING_MAX_DISTANCE_M` lat/lng box, at most `GROUPING_MAX_CANDIDATES`. `score_pair` (`dedup/grouping.py`, pure) compares the listing with each candidate listing. Vetoes come first: different bedroom counts (Zillow's per-bedroom building listings share address and photos), different units, or further apart than the limit. Then up to five signals, each 0–1: address (1 same canonical, 0.6 same street with a unit on one side), distance, photos (share of the smaller set with a pHash match within `GROUPING_PHASH_DISTANCE`), and rapidfuzz token-set similarity of title and description (`dedup/text.py`). Signals a listing lacks are left out rather than scored 0. The score is the weighted mean (`GROUPING_WEIGHT_*`), and a pair matches with at least `GROUPING_MIN_SIGNALS` signals, a score of at least `GROUPING_MATCH_THRESHOLD`, and an anchor: the same street address or at least half the photos, since a manager's ad copy repeats across units. The listing's own property and every matching one are the same unit. The one furthest along (`status_rank`; `unavailable` counts as the status it left; ties go to the oldest) survives and keeps its status, so no merge runs outside the state machine and a duplicate of a suggested or decided unit isn't notified again. A new listing joining gets a `grouped` audit event with the score and signals. Every other property is merged into the survivor (`merge`): listings, notes and emails move, the better match is kept, `merged_into_id` is set, and both get a `merged` audit event. The merged row keeps its own audit trail, which the survivor's timeline shows. Its Discord message is redrawn as merged with all buttons off, or taken over by the survivor if that has none. A new listing (a repost under a new id) that joins a unit whose listings are all removed relists it, the same way `restore_relisted` does: a `relisted` event follows the `grouped` one, and an `unavailable` survivor is restored by it. A survivor of a merge left `unavailable` with an active listing is restored as relisted. Merged properties are left out of every view and count. Their detail page redirects to the survivor, the API shows `merged_into_id` and answers 409 to changes, buttons answer with the survivor's number, and queued `inquiry.create` jobs act on the survivor. Since pHashes usually arrive after the first match, the image job regroups the listings it hashed. The property's `score` and `match_result` are its best listing's (`match_listing_id`); that listing's own newer result replaces it.

**Fixing grouping by hand.** The detail page can merge another property into the one shown (`POST /properties/{id}/merge`, `SqlPropertyStore.merge_properties`) and split a listing off a property with several (`POST /properties/{id}/listings/{listing_id}/split`, `split_listing`). Both are audited on both properties with the `dashboard` actor. A manual merge goes through the same `merge` as grouping, but the property whose page it is survives and keeps its status: the person chose. A split gives the listing a new property in `new` (its creation event says `split_from`) and records a `split` event on the old one. The old property drops its match if it came from that listing, takes its address from its new primary listing, and becomes `unavailable` if it has no active listing left. A `rerun_criteria` job with `listing_ids` then scores the listings involved against the active criteria, so the new property can be suggested on its own. Grouping never undoes either. It only merges, so a manual merge stays. A split is stored as `listing_separations` pairs (the split listing and each listing left behind), and `group_listing` skips any candidate that would put two separated listings under one property, taking the best match first. A listing that matches both halves of a split joins only one of them. Merging the two halves by hand deletes their separations.

**Money and rent periods.** Prices are integer minor units (cents) plus a currency code from a small registry in `domain/money.py`; USD is the default and other currencies are added by registering them. A `Price` keeps the amount (or range) and period the source quoted, and matching compares its monthly equivalent: nightly × 365/12, weekly × 52/12, monthly × 1. The factors are exact fractions and the result is rounded half-up once, to a whole cent. An unknown price is `None`, never 0. `NormalizedListing` (`domain/listing.py`) is the frozen shape every adapter returns; unknown fields stay `None`, and raw property-type labels are mapped onto `PropertyType` with unrecognised ones becoming `other`.

**Criteria versions.** The search profile is a frozen `Criteria` (`domain/criteria.py`). `CriteriaStore` (`db/criteria_store.py`) appends every save to `criteria_versions` as version `max + 1`, and never edits or deletes a version. Activating a version, new or old, clears the previous flag in the same transaction. A partial unique index (`WHERE is_active = 1`) makes a second active row impossible, and the first version saved is always active, so a non-empty history has exactly one. `diff(a, b)` lists the top-level fields that changed. Collections are stored sorted and de-duplicated, so equal profiles compare and serialize identically.

**Criteria editor.** `/criteria` edits the active profile. `web/criteria_form.py` maps the flat form onto `Criteria`. Blank inputs mean not set. Prices are typed in major units with one currency. ZIP codes, neighborhoods and keywords are one per line or comma. Property types, must-haves and `unknown_fails` are checkbox groups. Areas and nice-to-have weights are repeated `areas-<i>-*` / `nice-<i>-*` rows, which htmx adds with an out-of-band "add" button and a remove checkbox drops, so no client script is needed. Validation errors come back as 422 with a message beside each field (htmx is configured to swap 409/422). A valid save appends a version through `CriteriaStore`, and a save that changes nothing is reported, not stored. `/criteria/history` lists versions newest first with each one's diff against the one before it, and can activate any of them. "Re-run criteria" queues a `rerun_criteria` job pinned to the active version. Its handler (`pipeline/rerun.py`) runs `match_listing` on every stored listing and hands each result to a sink. Its listing source stays empty until #28 connects it to `SqlListingStore.active()` and the property store.

**Location matching.** `matching/location.py` checks a listing against the criteria's areas (haversine distance ≤ radius, in each area's own mi/km unit), ZIP codes (ZIP+4 compares as its 5-digit ZIP) and neighborhoods (case- and whitespace-insensitive). Any one match qualifies. A criterion the listing has no data for is skipped and noted as "location unknown". The result is `match`, `no_match` (everything was checked), `unknown` (nothing matched but something couldn't be checked), or `not_configured`, with a reason per check. The hard filters decide what `unknown` means. Addresses are parsed through the `AddressParser` protocol (`domain/address.py`) into a `ParsedAddress` with USPS-style normalization and a `canonical` string for dedup. `dedup/address.py` implements it for the US with `usaddress`, and `PassthroughAddressParser` handles other countries and input that won't tag.

**Hard filters.** `matching/filters.py` checks a listing against each hard constraint in the criteria: location, monthly price range, property type allow and deny, minimum beds, baths and sqft, furnished, move-in window, lease range, must-have amenities, and keyword allow and deny on title and description. Each rule (`FilterRule`) returns `pass`, `fail` or `unknown` with a human-readable reason. Rules the criteria don't configure are left out. Unknown means the listing lacks the data, for example no price, no bed count, or an amenity it never mentions. Unknown passes unless the rule is listed in the criteria's `unknown_fails`, so that choice is versioned with the profile. A quoted price range passes if it overlaps the wanted range, and a price in another currency is unknown. An unrecognized property type is unknown unless `other` is named explicitly. A listing available before the move-in window passes. A must-have that the amenity result rules out fails, while one that is only unmentioned is unknown. Keywords match case-insensitively on word boundaries. `evaluate_hard_filters(listing, criteria, amenities=..., parser=...)` is pure and returns every rule's verdict plus `passed`.

**Scoring.** `matching/scoring.py` ranks listings that pass the hard filters. Every scoring component has a weight in the criteria and earns a fraction of it from 0 to 1. A nice-to-have amenity earns its full weight when the listing states it, and nothing when it is ruled out or never mentioned. Two fit components are opt-in. Price fit (`price_fit_weight`, which needs `price_max`) earns more the lower the monthly price sits in the wanted range, using the midpoint of a quoted range and measuring from zero when there is no minimum. Extra beds (`extra_beds_weight`, which needs `min_beds`) earns half for one bed above the minimum and the full weight for two or more. The score is the earned share of the total weight, scaled to 0–100 and rounded half-up, so only the ratio between weights matters. Each breakdown item (label, points, max points, reason) uses the same 0–100 scale, so the items add up to the score. Criteria with nothing to score give every listing 100. `match_listing(listing, criteria, criteria_version=...)` runs the filters and scoring together and returns a `MatchResult` (passed, score, breakdown, every rule verdict, criteria version). Failed listings are scored too, but only passing ones are ranked. The result is a pydantic model that round-trips through JSON, and the property row (#27) stores it with the criteria version that produced it.

**Amenity extraction.** `domain/amenities.py` holds the one tag vocabulary (`Amenity`, e.g. `in_unit_laundry`, `pets_allowed`, `ac`). It also holds the `AmenityExtractor` protocol, whose `AmenityResult` keeps `present`, `absent` (explicitly ruled out, e.g. "no pets") and `unrecognized` adapter labels apart. A tag in neither set is unknown. `matching/amenities/` implements the protocol deterministically. `vocabulary.py` maps regex phrases to tags, and `keyword.py` scans clauses split at punctuation, commas and "but". A negator up to three words before a phrase, or right after it ("not included"), flips it, so negation never crosses a clause. Within a source, absent beats present. The adapter's own labels override the free text. "Cats ok" implies pets are allowed, and "no pets" rules out cats and dogs that weren't stated. `matching/amenities/llm.py` adds an optional LLM pass, which is off unless `LLM_PROVIDER=openai_compatible` with `LLM_BASE_URL` and `LLM_MODEL` set. It calls any OpenAI-compatible `/chat/completions` endpoint, so a local Ollama works. The reply must match a strict JSON schema (`present`/`absent` lists of tags). The keyword result always stands, and LLM verdicts only fill tags it left unknown. Pets are reconciled again after the merge. A transport error, timeout, non-2xx status, malformed reply or unknown tag is logged without listing text, and the keyword result is used alone. Successful LLM verdicts are cached in `amenity_extractions` (`db/amenity_cache.py`), keyed by a SHA-256 of prompt version, model, title, description and adapter labels. An unchanged listing never calls the model twice, and failures are not cached. `build_amenity_extractor(settings.llm, cache)` picks the extractor.

**Sources.** An adapter subclasses `SourceAdapter` (`sources/base.py`). It declares `name`, `display_name`, `capabilities` (needs a browser, has an API, supports geo search, provides contact details, requires an API key) and `default_enabled`. It implements `search(criteria)`, which returns `NormalizedListing`s, and optionally `fetch_detail(listing)`. Adapters are synchronous because they run in worker threads. `discover()` (`sources/registry.py`) imports every module under `sources/adapters/` and registers each concrete subclass into a `SourceRegistry`. Adding a source is just adding a module. `resolve_config` (`sources/config.py`) builds each adapter's `AdapterConfig`, falling back field by field from its entry in the `SOURCES_ADAPTERS` JSON to the global `SOURCES_*` defaults (interval, jitter, requests per minute, user agent, proxy, timeouts, max results; the API key and search locations are per adapter only). `enabled` has the same precedence as runtime settings. An `enabled` set in `SOURCES_ADAPTERS` pins the source. Otherwise the dashboard toggle stored in `sources.enabled` decides, and if that was never set the adapter's `default_enabled` applies. Naming an unknown adapter in `SOURCES_ADAPTERS` raises `SourceConfigError` instead of being ignored. An adapter whose capabilities say `requires_api_key` is disabled, with a `disabled_reason`, until its entry has an `api_key`. Per-adapter keys are redacted from logs and Sentry like every other secret. `search_locations` (place names, per adapter) and `max_results` serve sources that search by city or bill per result. Sources that can't be fetched directly go through a data provider. `sources/provider.py` defines the `DataProvider` protocol (a backend that runs a named job on some input and returns its items) and the `ProviderAdapter` base. That base checks the token and `search_locations`, runs `job` on `provider`, and leaves a subclass only `build_input` and `parse_items`. `sources/apify.py` is the one backend: `run_actor` starts an Apify actor run, long-polls it, and reads its dataset, with the token in a header. `ApifyAdapter` is `ProviderAdapter` on Apify, and Furnished Finder, Zillow and Airbnb use it. Craigslist is fetched directly through `SourceHttpClient`: one search page per site and category, then each posting it hasn't seen, with postings cached in the worker process so later runs fetch only new ones. A self-hosted backend would be another `DataProvider` (see `docs/adapters.md`, "Data providers and self-hosted alternatives"). It hands the items back with the input it sent, so a mapping can depend on the search (Airbnb prices a listing over the stay dates it asked for). `docs/adapters.md` records each source's access options and field mapping. Researched sources that aren't built yet are registered as stubs (`sources/stub.py`, `sources/adapters/stubs.py`). Their `implemented = False` makes `resolve_config` disable them with a "not built yet" `disabled_reason` that no pin or toggle overrides. `SqlSourceStore` (`db/source_store.py`) creates a `sources` row per registered adapter and records each run's success or failure (consecutive failures, last error truncated to 2000 chars, listings found).

**Source HTTP layer.** Adapters make requests through `SourceHttpClient` (`sources/http.py`), built from their `AdapterConfig`, which supplies the timeout, user agent and proxy. Each request goes through four steps. First, a robots.txt check (`sources/robots.py`), unless `respect_robots` is off. The file is cached per origin for 24 hours. A 4xx means no rules. A 5xx or unreachable file raises `SourceError` and is not cached, as RFC 9309 says. A disallowed URL raises `SourceBlockedError` before anything is sent. Second, every attempt, retries and robots.txt fetches included, takes a token from the adapter's `TokenBucket` (`sources/ratelimit.py`, `requests_per_minute`, no bursts, thread-safe). Third, a 429, a 5xx, a timeout or a transport error is retried up to `max_retries` times, with exponential backoff and full jitter (up to `2**n` seconds, capped at 60s). A `Retry-After` header replaces the backoff, and one over five minutes ends the attempt instead. Fourth, the response is classified. A 403, or an HTML 2xx page with a captcha or challenge marker in its first 64 KB, raises `SourceBlockedError` (adapters can add their own markers). Any other 4xx, or retries running out, raises `SourceError`. Both errors carry the URL and the status. `respect_robots` and `max_retries` follow the same `SOURCES_*` → `SOURCES_ADAPTERS` fallback as the other per-adapter settings.

**Browser layer (optional).** Sources that only render with JavaScript set `Capabilities.needs_browser` and load pages through `SourceBrowser` (`sources/browser.py`), headless Chromium driven by Playwright. Playwright is the `browser` extra and is imported only when a browser starts, so the app runs without it. `browser_unavailable_reason` checks `SOURCES_BROWSER_ENABLED` and whether Playwright is installed, without launching anything. When either is missing, `SourceRegistry.configured` disables every `needs_browser` adapter, even one pinned on in `SOURCES_ADAPTERS`, and puts the reason in `AdapterConfig.disabled_reason`. The worker stores it in `sources.disabled_reason` (`SqlSourceStore.set_disabled_reasons`). A missing Chromium binary raises `BrowserUnavailableError` at launch. Each browser context takes the adapter's user agent, proxy and timeout, and aborts image, font and media requests before they are sent. `SourceBrowser.render(url)` shares the adapter's `SourceHttpClient`, so robots.txt rules and the token bucket are the same as over HTTP: one token per navigation, while subresources the page loads itself are not counted. A 403 or a captcha marker raises `SourceBlockedError`, and Playwright errors and timeouts raise `SourceError`.

**Property state machine.** `domain/status.py` holds `PropertyStatus`, the actors (`dashboard`, `discord`, `system`, `api`) and `TRANSITIONS`, the full allow-list:

```
new → suggested → approved | denied
approved → inquiry_drafted → inquiry_sent → in_progress → responded | touring | applied → won | lost | archived
any active state → unavailable (listing disappeared) → back to that state
```

Beyond that path, `archived` is reachable from every state except itself and is terminal. Any state before the inquiry is sent can be `denied`, and `denied → approved` undoes a denial. `inquiry_drafted → approved` throws a draft away. `inquiry_sent → responded` covers a reply detected before anything else happened, and `lost` is reachable from any state after the inquiry is sent. Only the `system` actor moves a property into `unavailable`. Coming back from it, the property must go to the state it left, read from the latest audit event into `unavailable`, so a relisted property keeps the human decision that was made on it. People can still archive it. Moving to the same state is an error. `SqlPropertyStore.transition` (`db/property_store.py`) is the only status writer: in one transaction it checks the move with `check_transition` and writes the status, `status_changed_at` and an `audit_events` row (from, to, actor, actor detail, payload). The transaction takes the write lock up front, so of two concurrent clicks the second sees the first one's result and is rejected. A listing gets its property the first time it is matched (`_ensure`): it joins an existing property of the same unit when grouping finds one (see **Grouping**), otherwise it gets a new property in `new` with its geo and canonical address, and the creation is the first audit event (`from_status` NULL). The transition logic itself is in `_apply_transition`, so pipeline methods can run a transition and other writes in a single transaction.

**Property pipeline.** `PropertyPipeline` (`pipeline/properties.py`) connects ingestion and criteria re-runs to the store. `ListingIngestor` takes three hooks, and the worker plugs the pipeline into all of them:

- **`record`** gets every match (`SqlPropertyStore.record_match`). It creates the property if needed and stores `score`, `match_result` and `criteria_version_id`. If the match passes and the property is `new`, it moves the property to `suggested` (system actor) and queues a `notify` job, both in the same transaction.
- **`on_removed`** gets the listings `mark_missing` removed (`mark_gone`). A property moves to `unavailable` once none of its listings is active. States that can't become unavailable, such as denied, won, lost and archived, keep their status but get a `listings removed` event in place, so the gap is on record in every state.
- **`on_relisted`** gets listings that came back (`restore_relisted`). If the property had no other active listing and was gone (`unavailable`, or a `listings removed` event not yet followed by a relisting), the unit is relisted: a `relisted` event records the listing, `gone_since` (when the listings were all removed), and `price_before_minor`, `price_now_minor` and `currency` (the group's last price change before the listing was seen again, and the listing's monthly price now). An `unavailable` property returns to the state it left through that event. Any other status is kept and the event is recorded in place. A second call for the same listings records nothing, so a unit that is denied and then reappears at a lower price stands out on its timeline ("Relisted (listing #7) after 12 days · $2,400.00 → $2,100.00/mo"). The relisting doesn't notify again.

If a hook raises, the error is logged and the run still succeeds, like a failed match.

The `rerun_criteria` job scores `SqlListingStore.active()` with the amenities stored at ingest and calls the same `record`. A match only ever moves a property out of `new`. Any other state, whether suggested or decided by a person, keeps its status and gets only the new score, so a re-run never regresses a decision or notifies twice.

**Snooze** (`snooze`, `PIPELINE_SNOOZE_HOURS`) is not a status. It sets `snoozed_until` and writes an audit event whose `from_status` and `to_status` are the same, so the trail shows who snoozed. Restore lookups skip these events. `SqlPropertyStore.query(now=...)` and the dashboard's `search` hide properties snoozed past `now` by default. The scheduled `unsnooze_expired` job (every `PIPELINE_UNSNOOZE_INTERVAL_MINUTES`) clears expired snoozes. For a property still `suggested`, it also queues `notify` again.

**Notifications.** The worker consumes `notify` jobs with `NotifyPost` (`notify/post.py`). It skips a property that is gone, no longer `suggested`, or snoozed past now, and it is a no-op until both `DISCORD_BOT_TOKEN` and `DISCORD_CHANNEL_ID` are set. Otherwise it posts `match_message` to `DISCORD_CHANNEL_ID` and saves the channel and message id on the property (`SqlPropertyStore.attach_message`). If the status or snooze changed while the post was in flight, that same transaction queues a message sync. A `notify` for a property that already has a message (a snooze that ran out) posts a new message, so the channel is pinged again. The old message is then synced once more, which greys out all of its buttons and adds "reposted" to its footer. `record_match` and `unsnooze_expired` don't queue a second `notify` while one is still waiting to run. Discord errors raise and the queue retries. If the worker dies between Discord accepting the post and the ids being saved, the retry posts the property twice. That is accepted rather than adding a two-phase handshake.

**Migrations and foreign keys.** SQLite can't alter most of a table in place, so Alembic rebuilds it, and dropping the old table with foreign keys on would cascade into every table pointing at it (adding `listings.property_id`'s foreign key would have emptied `listing_images` and `price_history`). Migrations therefore run as one transaction on a connection with foreign keys off (`foreign_keys_off` in `db/engine.py`), finish with `PRAGMA foreign_key_check`, and turn enforcement back on before the connection returns to the pool.

**Discord.** furnest uses an HTTP interactions endpoint (Ed25519-verified), not a gateway bot. The web process must reply within 3 seconds, so it sends a deferred response, records the interaction ID for idempotency, applies the state change, and enqueues slow work (email sending, enrichment) for the worker. The worker then edits the original message to show the new state. [discord-setup.md](discord-setup.md) covers creating and wiring the Discord application.

**Discord interactions.** `POST /discord/interactions` (`web/routes/discord.py`) is outside dashboard auth and CSRF because Discord calls it, not a browser. With no `DISCORD_PUBLIC_KEY` it answers 404. Otherwise it checks the Ed25519 signature in `X-Signature-Ed25519` over `X-Signature-Timestamp` + raw body (PyNaCl, `notify/interactions.py`). It also rejects timestamps more than `DISCORD_INTERACTION_MAX_AGE_SECONDS` (default 300) from our clock. Either failure gets a 401, which is what Discord's endpoint-registration probe expects. A PING gets a PONG without touching the database. Every other interaction id is inserted into `discord_interactions` (with a savepoint) in the same transaction as the work it triggers. A repeat of a known id gets a deferred-update ack and does nothing. If the work fails, the record rolls back, so Discord's retry still counts. Rows older than a day are deleted as new ones arrive, since the timestamp window already shuts out older replays. `InteractionDispatcher` (`web/discord_dispatch.py`, on `app.state.discord_dispatcher`) maps (interaction type, button action) to a handler that returns the immediate response body. A click on one of our buttons with no handler queues a message sync and is acked with type 6 (deferred update). Anything else gets an ephemeral "not supported" reply.

**Discord buttons.** `web/discord_actions.py` registers the four buttons. Each handler runs in the endpoint's transaction, using the session-level `transition_in`, `deny_in` and `snooze_in` from `db/property_store.py`, so the state change commits together with the interaction record. Every change is audited as actor `discord`, with `actor_detail` set to `name (user id)`. **Approve** works on a `suggested` or `denied` property; it is refused on a drafted inquiry, even though the state machine allows that move, so a stale click can't throw away a draft. **Deny** answers the click with a modal (type 9) holding one optional paragraph input, `reason`. The modal's submit carries the same `custom_id`, and it denies the property and saves the reason as a note. **Inquire** approves a `suggested` property, then queues an `inquiry.create` job with `property_id`, `actor` and `actor_detail`, unless one is already pending for that property. `request_inquiry_in` (`email/inquiry.py`) does both steps, and the dashboard's Inquire button calls it too. The job drafts the email and applies `INQUIRY_MODE` (see **Inquiry flow**). **Snooze** sets `snoozed_until` to now plus `PIPELINE_SNOOZE_HOURS`. An action that no longer applies, for example after a click on a stale message, gets an ephemeral reason and changes nothing. These are answered, not raised, so the interaction id is still recorded.

Once a property has a message, every status change and every snooze or unsnooze queues a `discord.message_sync` job (`notify/sync.py`) with `property_id`, `channel_id` and `message_id`, in the same transaction. This happens in `_apply_transition` and `_audit_in_place` in the property store, so it doesn't matter whether the change came from the dashboard, the API, a button or the system (`mark_gone`, `restore_relisted`, `unsnooze_expired`). A button click also queues one for the message it came from, in case that is an older message. Jobs are deduplicated by message id, but only against jobs that haven't started: a running sync may already have read the old state. The worker renders the message again from the database with `match_message`. The embed footer shows the status, and an active snooze, and `disabled_actions` greys out the buttons that no longer apply. It then edits the message with the bot token, not the interaction token, because the token expires after 15 minutes and the queue may retry later than that. The job is a no-op when Discord isn't configured, and a deleted message (404) is dropped. Rate limits and other Discord errors raise, so the queue retries.

**Discord messages.** `notify/embeds.py` turns a `PropertyDetail` (the detail page's read model) into a message payload. The payload has one embed: the listing title linking to the source, the first photo, monthly price, beds and baths, the score with its top three contributors, and links to the source and the dashboard page at `BASE_URL`. Under the embed is a row of Approve, Deny, Inquire and Snooze buttons, which can be disabled one by one. `allowed_mentions` is always empty, so scraped text can't ping anyone. Listing text that ends up in markdown is escaped, and every string is cut to Discord's limits. Each button's `custom_id` is `furnest:<action>:<property id>` (`notify/custom_ids.py`); `parse_custom_id` returns `None` for anything else. `DiscordClient` (`notify/discord.py`) creates and edits messages with the bot token. It sleeps out a route whose `X-RateLimit-Remaining` hit 0, keyed by method and channel. It waits out a 429's `retry_after`, and a global 429 blocks every route. A wait over 60s, or more than five 429s in a row, raises `DiscordRateLimitedError` instead of blocking. It retries 5xx and transport errors with jittered backoff (`DISCORD_MAX_RETRIES`). A 404 raises `DiscordNotFoundError`, and any other error raises `DiscordError` with Discord's error code. `discord_client(settings)` is `None` until both `DISCORD_BOT_TOKEN` and `DISCORD_CHANNEL_ID` are set. Payload snapshots live in `tests/fixtures/discord/`.

**Daily digest.** With `DISCORD_DIGEST_TIME` (HH:MM in `TIMEZONE`) set, `schedule_digest` (`notify/digest.py`) gives the worker a daily cron job (`Worker.schedule_daily`). That job only queues a `discord.digest` job for the local date, and only if no job for that date exists in any state. So the digest goes out at most once a day, even with several workers or a restart, and the queue retries it if Discord is down. A day the worker is down at that time gets no digest. `DigestPost` posts one embed:
- the property count in each non-empty status, snoozed properties included;
- the top `DISCORD_DIGEST_TOP` properties that became `suggested` in the last 24 hours and are still waiting, best score first, each linking to its dashboard page.

**Scheduling and locking.** At startup `schedule_sources` (`pipeline/schedule.py`) ensures a `sources` row for every adapter, stores each `disabled_reason`, and registers one scheduled job, `source:<name>`, per source that can run. Each job uses that source's interval plus random jitter and its run timeout (`SOURCES_RUN_TIMEOUT_SECONDS`, overridable per adapter). Before a run the worker takes the DB lease `scheduled:source:<name>` in `job_locks`, so overlapping runs of the same source are impossible, even across workers and restarts. Leases expire if the worker dies. Every source has its own job and its own daemon thread per run, so a slow, stuck or failing source never holds up the others. Each run resolves the dashboard toggle again and skips a source that is now disabled, which is why a source toggled off is still scheduled: turning it back on takes effect without a restart. Sources pinned off in `SOURCES_ADAPTERS` or unable to run are not scheduled. A successful run resets `consecutive_failures` and stores `listings_found`. An error or a timeout bumps `consecutive_failures`, stores `last_error` and goes to Sentry tagged with `source`. When a run times out, `ctx.cancelled` is set, and the ingestor throws away a search that returns after that instead of storing it late. The run also passes `DISCORD_ALERT_AFTER_FAILURES` (default 3, and 0 turns it off) to the source store. The failure that brings `consecutive_failures` up to that number queues a `discord.source_alert` job with `event: failing`, the count and the error, in the same transaction. The first success after that queues `event: recovered`. Only the crossing alerts, so an outage posts one alert however long it lasts. `SourceAlertPost` (`notify/alerts.py`) posts a red or green embed with the source's display name, the error in a code block and a link to `/sources`.

**Dashboard.** `/` (`web/routes/pages.py`, view-model in `web/property_views.py`) is the main working view. Its tabs group statuses: suggested, new, approved, in progress (`inquiry_drafted` through `applied`), won / lost, denied, unavailable, archived, and all (everything except archived). Each tab shows its count. The list view pages through one tab, 25 at a time. The board view shows every tab except all and archived as a column, each capped at 25 cards with a link to the full list. `SqlPropertyStore.search` does the reading. It joins each property to its primary listing (the lowest-id active listing, or the lowest-id listing if none is active) for title, price, beds and baths, and the source link. Text search is a case-insensitive substring match on the listing title or the canonical address, with `%` and `_` taken literally. Sort is by score (best first), monthly price (cheapest first) or newest, with unknowns last and ties broken newest first, so paging is stable. Snoozed properties are hidden unless "include snoozed" is on. `status_counts` gives the tab counts with the same filters. All filters live in the query string, and bad values answer 422. The filter form is a plain GET that works without JavaScript. With htmx, the form, tabs, pages and the 300 ms-debounced search box fetch only the results fragment (`dashboard/_results.html`). The fragment updates the form's hidden tab field out of band, and the response's `HX-Push-Url` is the canonical URL with defaults left out. Cards show no photos, to keep the list light; each card's title links to the property's detail page.

**Property detail.** `/properties/{id}` (`web/routes/pages.py`, template `properties/detail.html`) shows one property whole, read in one transaction by `SqlPropertyStore.detail`. The page has a header with the status, score, price, size, address, any snooze, and a manual-contact callout (see **Manual contact**). Below it are the photo gallery (every listing's photos, primary listing first, each URL once), the listings table (source link, monthly price with the price history, size, first and last seen, a removed badge), the property's price history when it has at least two price changes (every listing's `price_history` rows in one timeline via `property_price_points`, newest first, each with its source, its monthly price and the change from the previous one, under a first · lowest · now summary; `price_timeline` in `web/property_views.py`; the API returns the same points, oldest first, as `price_history` on the property detail), the score breakdown and hard-filter verdicts from the stored `MatchResult`, the primary listing's description, and the audit timeline, newest first. Email log (P6), enrichment and risk flags (P8) are placeholders until those phases fill them. Photos are hot-linked from the sources' CDNs: the CSP allows `https:` images (only images), and each `<img>` sends no referrer. #49 may serve local copies instead. Descriptions go through `web/html.py`. HTML is cleaned with nh3, keeping only `p`, `br`, lists and bold or italic, with no attributes, and `script`, `style` and similar tags lose their content. Plain text is escaped and split into paragraphs. An unknown id answers 404.

**Notes.** Any property can have notes: markdown, timestamped, as many as you like, each with its actor (`notes` table). The detail page lists them newest first and has a form to add one (`POST /properties/{id}/notes`). `SqlPropertyStore.add_note` strips the body and rejects an empty one or one over 10,000 characters (422 on the page). A note is rendered by `render_markdown` in `web/html.py`. markdown-it renders CommonMark with raw HTML off, so tags in a note show as text, and nh3 then keeps only formatting, code, quotes, headings and `http`/`https`/`mailto` links, with `rel="noopener noreferrer nofollow"` and no images. Deny (`POST /properties/{id}/deny`, shown while the state machine allows it) takes an optional reason. `SqlPropertyStore.deny` writes the transition, and the reason as a note, in one transaction, and the audit event points at that note with `payload.note_id`. The timeline shows that as "(reason in notes)". A deny the state machine forbids answers 409. The bulk deny (#32) uses the same method, and Discord's Deny modal uses its session-level twin `deny_in`, which wraps the note and the transition in a savepoint so a refused deny leaves no note.

**Status actions.** The detail page has a button for each move the dashboard may make from the current state. `allowed_targets(status, Actor.DASHBOARD)` in `domain/status.py` lists the targets that `check_transition` would accept, so `unavailable` is never offered and an unavailable property can only be archived. Deny keeps its own form, the one with the reason. A button posts to `POST /properties/{id}/status`, which calls `SqlPropertyStore.transition` with the `dashboard` actor and redirects back to the page (303). A move the state machine forbids, for example from a stale page, re-renders the page with the reason (409). Archive asks for confirmation because it is terminal. The list view adds a checkbox to each card and a toolbar to deny or archive the selected properties (`POST /properties/bulk`, at most 100). `apply_bulk` in `web/property_views.py` moves each property in its own transaction and skips, with the reason, those it may not move. With htmx the results re-render in place with a notice of what moved and what was skipped. Without htmx the post redirects back to the list. An empty selection is a 422, and one where nothing could move is a 409. All of these are htmx posts (boosted forms on the detail page) that carry the CSRF token, and they work as plain form posts without JavaScript.

**JSON API.** `/api/v1` (`web/routes/api.py`, bodies in `web/api_models.py`) is for scripts and automation: `GET /properties` (status/text filters, sort, `limit`/`offset` paging, snoozed hidden unless `include_snoozed`), `GET /properties/{id}` (match, listings, audit trail, notes), `GET /properties/{id}/listings`, `POST /properties/{id}/transitions` (`{"to": ..., "reason": ...}`, where only a deny takes a reason, saved as a note) and `POST /properties/{id}/notes`. It accepts only `Authorization: Bearer <AUTH_TOKEN>` (`require_bearer`), never the session cookie, so CSRF never applies. Errors are always JSON `{"detail": ...}`: 401, 404, 409 with the state machine's reason, 422. Changes are recorded with the `api` actor, which has the dashboard's rights (migration 0009 widened the actor CHECK constraints). Responses are Pydantic models built from the store's dataclasses, so the store can change without changing the API. Listings leave out the source's `raw` payload. The OpenAPI schema covers only `/api/v1` (HTML routes are `include_in_schema=False`) and is served at `/api/openapi.json` and in Swagger UI at `/api/docs`, both behind auth (Bearer or session). FastAPI's own docs routes stay off because they load Swagger UI from a CDN and would be public. Swagger UI is vendored under `static/vendor/swagger-ui/` and started by `static/js/api-docs.js`, which keeps it inside the self-only CSP.

**Source health page.** `/sources` (`web/routes/sources.py`, view-model in `web/source_health.py`) lists every registered adapter, including ones with no `sources` row yet. For each it shows a status (ok, failing, never run, disabled, unavailable), last run and last success, listings found, consecutive failures, the number of failed `source_runs`, and the last error. Errors are autoescaped and cut to 160 characters, with the full text in a `<details>`. Under the table are each source's 10 most recent runs. The web process resolves `enabled` the same way the scheduler does, but it never probes for a browser. It shows the `disabled_reason` the worker stored instead. The enable toggle writes `sources.enabled`, and the scheduler picks the change up on the next run. A source pinned in `SOURCES_ADAPTERS` or unable to run answers 409. "Run now" queues one `run_source` job (`max_attempts=1`), unless one for that source is already queued or running. Its handler, `RunSourceNow`, takes the same `scheduled:source:<name>` lease as the scheduled job. If the source is already running, the job does nothing, because that run is the one the user asked for. Otherwise it runs the source through `SourceRun` and records the outcome on the `sources` row like a scheduled run.

**Email sending.** Nothing sends mail directly. `queue_email` (`db/email_store.py`) runs in the caller's transaction: it inserts an `emails` row (`queued`, with the final subject and body, the From address and a Message-ID made once from the From domain) and queues an `email.send` job for it, so the email exists if and only if the caller's change commits. The worker's `EmailSend` (`email/send.py`) builds the message (`email/smtp.py`) and sends it through `SmtpSender`, one connection per message, over implicit TLS, STARTTLS or plain (`SMTP_SECURITY`), with `SMTP_TIMEOUT_SECONDS` on every operation and login only when `SMTP_USERNAME` is set. A 5xx reply (refused recipient or sender, bad credentials) marks the row `failed` and isn't retried. Anything else (4xx, connection errors, timeouts, SMTP not configured) records the error and attempt count and raises, so the queue retries with backoff; the row becomes `failed` when the last attempt fails. A row already `sent`, or still a `draft`, is skipped. Delivery is at least once: a worker that dies between the server accepting a message and the row being marked `sent` sends it again, with the same Message-ID. Logs carry the email id and recipient domain, never the address list or credentials.

**Inquiry templates.** Inquiry copy is Jinja2 that the user edits at `/email-templates` (`web/routes/email_templates.py`). Templates live in `email_templates` (name, subject, body), and migration 0012 seeds `default`, which can be edited but not deleted. The signature is the `email_signature` row in `settings`, so every template shares it. Since templates are untrusted input, `email/templates.py` renders them in Jinja's `ImmutableSandboxedEnvironment` with `StrictUndefined`, against an `InquiryContext` that holds only plain values: `listing` (title, url, source, formatted monthly price, one-line address, city, size, beds, baths, sqft, availability, lease limits), `contact_name`, `move_in_date` and `lease_months` (the active criteria's `my_move_in_date` / `my_lease_months`), and `signature`. The sandbox refuses underscore attributes and mutating methods, and a misspelled name raises instead of rendering blank. Every failure comes back as a `TemplateRenderError` that names the part (subject or body) and the line where it can. The output is plain text and is not HTML-escaped. The subject is folded onto one line, so a newline can't add headers. Saving renders the template against a sample listing first and refuses it (422) if that fails. The editor's preview posts the form through htmx on each edit (debounced) and shows the sample inquiry with the real signature and criteria; without JavaScript, the Preview button returns the whole editor. `context_for(listing, criteria, signature)` builds the context for a real listing, for the inquiry flow.

**Inquiry flow.** Discord's Inquire button and the detail page's Inquire button (`POST /properties/{id}/inquire`) both call `request_inquiry_in`. It approves a `suggested` property and queues `inquiry.create`, unless one is already pending. The handler, `InquiryCreate` (`email/inquiry.py`), does nothing unless the property is still `approved`, so a duplicate or stale job is harmless. Otherwise, in one transaction, it renders the `default` template (falling back to the built-in text if that row is gone) for the primary listing, the active criteria and the signature. It logs the result as an outbound `emails` row with status `draft`, with `to_address` taken from the listing's contact email (NULL if there is none). Then it moves the property `approved → inquiry_drafted`, audited with the requesting actor. `INQUIRY_MODE` (env, or the stored runtime setting) decides what happens next. In `auto`, the draft is queued straight away (`send_draft_in`: status `queued` plus an `email.send` job), unless it has no recipient. In `review`, or with no recipient, the draft waits in the review queue at `/inquiries` (`web/routes/inquiries.py`). The queue shows every `draft` or `failed` outbound email whose property is still `inquiry_drafted`, as a form with To, Subject and Body. **Send** checks the form (`review_edit`: a valid address, a non-empty subject folded onto one line, a non-empty body within the template limits), saves it to the row, resets `error` and `attempts`, and queues it. **Discard** deletes a draft (a failed email stays in the log) and moves the property back to `approved` with the `dashboard` actor. Both answer 409 once the email or its property has moved on. The property becomes `inquiry_sent` only when the server accepts the message: `SqlEmailStore.mark_sent` makes that move (actor `system`, payload `email_id`) in the same transaction. A permanently failed inquiry goes back to the queue with its error. The detail page's plain status buttons don't offer `inquiry_drafted`, `inquiry_sent`, or leaving `inquiry_drafted` other than by archiving, so a property can't end up drafted without a draft. Drafting doesn't need SMTP. Without a From address, the draft is logged with `from_address` NULL and a placeholder Message-ID (`@furnest.invalid`), and `auto` mode leaves it for review. Sending needs SMTP: `send_draft_in` raises `SmtpNotConfiguredError` (409 on the queue), and when the draft has no From address it fills it in and makes a fresh Message-ID. The detail page's email log lists every email about the property, newest first, with its rendered body.

**Manual contact.** Some listings give no email address because the source only relays messages through its own site (Furnished Finder, Zillow and Airbnb build every listing with `Contact(platform_only=True)`, and so does Craigslist unless the poster wrote an email address into the description). `properties.manual_contact_required` marks these properties. `SqlPropertyStore` sets it when it creates the property, and `record_match` recomputes it from the primary listing's contact email on every match. When the flag flips on a property that has a Discord message, the message is synced. Migration 0014 backfilled the flag. The Discord embed adds a **Contact** field that links to the source. The detail page shows a "Contact on <source>" callout. While the draft waits, the page also shows the message, ready to copy: subject and body, each with a Copy button (`static/js/copy.js`, `navigator.clipboard`, falling back to selecting the text). A **Mark as sent** form posts to `POST /inquiries/{id}/mark-sent` with `back=property`. The review queue offers the same button on every draft and failed inquiry, plus the source link for one without a recipient. Mark as sent checks the text (`manual_edit`: the same subject and body rules as `review_edit`, with no address), and `mark_sent_manually_in` saves it to the row as `sent`, with `sent_at` set and no recipient. In the same transaction, it moves the property `inquiry_drafted → inquiry_sent` (actor `dashboard`, detail `sent manually`, payload `{email_id, manual: true}`). The email log shows such a row as "sent by hand". It answers 422 for bad text, 404 for an unknown email, and 409 once the email or its property has moved on.

**Reply detection (IMAP).** Optional and off unless `IMAP_ENABLED=true`, which needs `IMAP_HOST`, `IMAP_USERNAME` and `IMAP_PASSWORD`. `email/imap.py` schedules `ImapReplyPoll` (`email.imap_poll`) every `IMAP_POLL_INTERVAL_SECONDS`. A poll first asks `awaiting_reply` for the inquiries still waiting: emailed ones (not sent by hand) whose property is `inquiry_sent` or `in_progress`. With none, it doesn't connect. Otherwise it opens `IMAP_FOLDER` read-only (`SELECT … readonly`, and only `BODY.PEEK` fetches, so nothing is marked as read), searches `SINCE` the oldest of those inquiries (capped at `IMAP_LOOKBACK_DAYS`, minus a day for time zones), and fetches only the threading headers of what it finds. A message whose In-Reply-To or References quotes an inquiry's Message-ID, and which isn't from furnest's own address, is fetched in full. `record_reply_in` logs it as an `inbound` row with status `received` (From, To, subject, the plain-text body or HTML reduced to text, the Date header as `sent_at`) and moves the property to `responded` (actor `system`, detail `reply received`, payload `{email_id, reply_to}`), both in one transaction. The reply's own Message-ID is unique in the log, so a later poll finding it again changes nothing. A reply with no Message-ID gets one derived from its content. Other mail is never downloaded past those headers, stored or logged, only counted. IMAP errors fail the run, which the worker reports, and the next interval tries again. Migration 0015 adds `received` to the status constraint. The detail page's email log shows replies as "Received … from <sender>".

**Geocoding.** `enrichment/geocoding.py` defines a `Geocoder` protocol: `geocode(Address)` returns a `GeocodeResult` (coordinates, the geocoder's canonical `Address`, display name and a `GeocodePrecision` from `address` down to `region`), or `None` for no match. `GEOCODING_PROVIDER` picks the implementation through `build_geocoder`. `none` (the default) is `NullGeocoder`, which never makes a request. `nominatim` is `NominatimGeocoder`, which sends a structured `/search` to `GEOCODING_BASE_URL` and requires an identifying `GEOCODING_USER_AGENT`, as Nominatim's usage policy does. It holds one token bucket at `GEOCODING_REQUESTS_PER_MINUTE` (default 60, the public instance's 1 req/s) and adds `key` only when `GEOCODING_API_KEY` is set. The query is the address lower-cased, with whitespace collapsed and any trailing unit (`Apt 4B`, `#4b`) dropped, because geocoders resolve buildings, not doors. An address with no street, city or postcode isn't looked up. `CachedGeocoder` puts `geocode_cache` (`db/geocode_cache.py`) in front of the provider, keyed by a SHA-256 of the provider and query. A result is kept forever. A "not found" is kept for `GEOCODING_MISS_TTL_DAYS` and then asked again. Timeouts, HTTP errors (429 included) and malformed replies raise `GeocodingError` and are never cached. A city- or postcode-level fallback is marked by its precision, so callers can refuse to treat a centroid as a listing's location. Nothing calls the geocoder yet; the alternatives finder (#54) is its first consumer.

**Job queue and timeouts.** `jobs` rows go `queued → running → succeeded`. A failed run goes to `failed`, with `run_after` pushed back by exponential backoff, and to `dead` once its attempts run out. A claim counts the attempt and leases the row (`locked_by`/`locked_until`) for longer than the job's timeout. Rows whose lease has expired are reclaimed, and `complete`/`fail` only change a row the caller still holds. Each run gets its own daemon thread. A timeout stops the wait and sets `ctx.cancelled`, but Python can't stop the thread itself, so handlers are idempotent and cooperative. On shutdown the worker drains for up to `WORKER_SHUTDOWN_TIMEOUT_SECONDS`, then puts unfinished jobs back on the queue without counting the attempt.

**Configuration.** Infrastructure and secrets come from environment variables (pydantic-settings, documented in `.env.example`). User preferences edited in the dashboard (criteria, templates, toggles) live in the DB. Env vars always win for anything defined in both places.

**Safety.** Scraped HTML is never rendered raw: it is sanitized with nh3 or reduced to text. Pages send a strict CSP: scripts, styles and form targets are self-only, and images are self, `data:` or `https:` (listing photos). So the brand icons (`web/static/brand/`, see [BRAND.md](BRAND.md)) are served locally and fonts are the system stack. `/favicon.ico` is a public route at the root, because browsers request it there before anyone signs in. htmx is vendored and configured not to inject inline styles or `eval` code, so the CSP needs no `unsafe-*` exceptions. Logs redact secrets. The container runs as a non-root user. The dashboard is protected by a single token (signed HttpOnly SameSite cookie or `Authorization: Bearer`, constant-time comparison, CSRF on forms, rate-limited login).

## Conventions

- `uv` for dependencies, with `uv.lock` committed. `ruff` for lint and format, `mypy --strict`, `pytest` with coverage. All four must pass before merge.
- Tests make no live network calls. Adapters are tested against recorded fixtures, which are sanitized of personal data and refreshed by hand with `scripts/capture_fixture.py` (see [CONTRIBUTING.md](../CONTRIBUTING.md#refreshing-fixtures)).
- Every schema change ships with an Alembic migration and a migration test.
- Every new setting is documented in `.env.example`.
- Optional integrations (Sentry, LLM extractor, reverse image search, IMAP, Prometheus, Playwright) do nothing when unconfigured.
- Work is tracked one issue per PR: branch `issue-<n>-<slug>`, PR body says `Closes #<n>`.
